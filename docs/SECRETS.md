# Secrets

Every credential HushBox depends on, what replacing it costs, and the design that keeps that
cost at its floor. Read this before adding a GitHub secret, adding a `secret()` entry to the env
registry, or responding to a leak or a loss. Procedures live in `docs/runbooks/secrets/`, one file per
credential family; every secret declares its family, and the inventory below links each row to
its file.

## The three questions every secret answers

A secret is declared in code with three independent answers, and the inventory at the end of
this document is generated from those declarations.

- **Replacement class** — what it costs to replace the value after a leak, or on a schedule.
  `transparent`: mint a new value, set it, deploy; downtime and a forced sign-in are accepted.
  `adminAction`: an operator runs a procedure; users do nothing. The two remaining classes,
  `userMigration` (every user performs an explicit step) and `dead` (the account or the company
  cannot recover), are forbidden: a test refuses any declaration that names them, so a secret
  cannot be added in a state worse than admin action.
- **On loss** — what happens when the value is gone and no attacker has it. Every GitHub secret
  has an offline copy, so loss is restoration (`restoreFromCopy`); vendor-issued credentials are
  re-minted (`reissueAtVendor`); per-deploy values are re-minted by the next deploy
  (`mintedPerDeploy`).
- **Leak impact** — what an attacker gains by reading the value, from `companyEnding` to
  `nuisance`. This axis is deliberately separate from the replacement class: a credential can be
  trivial to replace and still company-ending to expose.

The declaration also carries a description, the store the value lives in, what users notice
during a replacement, the other secrets it must change together with, and the credential
family. A family's runbook holds the linear steps to obtain the value and, for an admin-action
family, the steps to replace it.

## Rules

**One live value per secret.** A secret has exactly one valid value at a time. No key ring, no
overlap window, no code path that accepts an old value beside a new one. A replacement is a hard
swap, and the downtime it costs is accepted. This keeps every verifier and every seal a
single-key operation and keeps rotation out of the request path entirely.

**The offline copy is written before the value is set anywhere.** Every GitHub secret has a copy
held outside production. The copy is what makes loss a restoration rather than an incident.
Where it is held and how it is written are deliberately recorded nowhere in the repository.

**A restore-from-copy secret is also escrowed by machine.** The escrow job captures every
secret whose loss class is `restoreFromCopy` — the inventory's `Escrowed` column — before the
deploy that publishes it, encrypted to recipients whose private identities live outside this
system and appended to an object-locked bucket. One job per GitHub environment, because a job
reads repository-scoped secrets plus the one environment it declares, so a set spanning two
environments needs two jobs, and a set the workflow declares no job for — a
`ci`-environment variant of an escrowed declaration — has its offline copy and nothing else.
The bucket, its keys, and the restore drill: `docs/runbooks/secrets/backblaze-key.md`.

**Coupled secrets ship in one publish.** Two halves of one credential, or two values one vendor
issues together, are declared coupled, and the production deploy publishes the Worker's whole
secret set inside its code upload, so the set goes live in one Worker version with the code that
reads it, and not at all when the deploy fails before the upload. A generated deploy block that
published them one at a time would put a mismatched pair live between two publishes, and a test
refuses a second publish site.

**Declarations are enforced, and the inventory is generated.** The env registry
(`packages/shared/src/env/env.config.ts`) carries a declaration on every entry that holds a
`secret()` marker in any mode; GitHub secrets that workflows reference but the registry does not
hold are declared beside it in `packages/shared/src/env/ci-secrets.ts`. Tests assert that every
credential-bearing entry declares, that every `secrets.NAME` in any workflow is declared exactly
once, that no declaration names a forbidden class, that every family has a runbook and no
runbook is orphaned, and that an admin-action family's runbook carries a replacement
procedure. The inventory table below is emitted by `pnpm generate:env` and drift-checked in
CI; never edit it by hand.

## The password secret: per-user material under one key

OPAQUE is the password protocol. Its server-side material — an OPRF seed and an AKE keypair — is
what every stored registration record is cryptographically bound to, and no design can change a
user's material without that user typing their password. So the design makes that material
**per user, and replaceable without ever changing it**:

- At registration the server mints random OPAQUE material for that user and stores it in the
  user's row, sealed under one global key-encryption key (`OPAQUE_KEK`). The row also carries the
  KEK's fingerprint, a short one-way hash of the key that identifies which key sealed the blob and
  is not itself secret.
- At login the server opens the user's blob under the KEK and runs the protocol on the material
  inside. The material never changes across a rotation, so the user's record stays valid.
- A database dump alone yields nothing: the material is ciphertext, and a password guess can only
  be tested against a record by running the OPRF with that material. Every guess must go through
  the server and its rate limits.
- Rotating the KEK, or replacing a leaked one, is an admin action: an ops-runner job takes the
  current key and the next one, re-seals every row, and exits when no row remains on the old
  fingerprint. The API is down for the job and the deploy that follows. No user is involved.
  `docs/runbooks/secrets/opaque-kek.md`.
- Losing the KEK is a restoration from the offline copy. A leaked copy costs one re-seal, which is
  what makes holding a copy safe.

**The one case rotation does not cover.** An attacker holding both a database dump and the KEK
that sealed it already holds every user's material in the clear, and re-sealing cannot take it
back. Those records stay attackable offline at the cost of one key-stretching evaluation per
guess, and that user's AKE key lets the attacker impersonate the server to them, until the user
changes their password, which mints fresh material. The response to that event is disclosure and
a forced password change. It is a compromise response, not a rotation, and every
end-to-end-encrypted design shares it.

Two further secrets are deliberately separate from the KEK, so each rotates on its own
lifecycle:

- **`TOTP_ENCRYPTION_SECRET`** seals each user's stored TOTP secret. The blob carries the key's
  fingerprint as its key id, bound into the authenticated data, so a substituted id fails
  authentication rather than selecting another key. Replacement is the same re-seal job
  (`docs/runbooks/secrets/totp-encryption-secret.md`). A blob that cannot be opened under the live key
  yields a typed "stranded" verdict at every gate that consumes it, and an admin operation can
  clear stranded second factors reversibly; that operation is the fallback for a bad offline copy,
  never the primary path.
- **`ENUMERATION_DECOY_SECRET`** derives the fake registration record and recovery dummies served
  for unknown identifiers. Nothing stored depends on it. Replace it rarely and with a reason: an
  attacker sampling one unknown identifier across a change learns the account does not exist.

## Secrets users notice

- **`IRON_SESSION_SECRET`** seals every session cookie. Replacing it signs everyone out once.
- **The VAPID keypair** (`VAPID_PRIVATE_KEY`, `VAPID_PUBLIC_KEY`, `VITE_VAPID_PUBLIC_KEY`) signs
  browser push. The push protocol binds the public key into each subscription when it is created,
  so a swap invalidates every existing subscription. Each browser re-subscribes on its next load
  without a prompt; pushes between the swap and that load are lost. The three values are coupled
  and the frontend copy is a build input, so a swap is one deploy carrying all three.
  `docs/runbooks/secrets/vapid-keypair.md`.
- **`VITE_HELCIM_JS_TOKEN`** is compiled into the web bundle and the mobile bundles. A native
  client's card form works again once it takes the next over-the-air update.

## Credentials held in no store

These are real and no repository artifact holds them, so no declaration covers them and no
inventory row exists. Their protection is account security, not replacement.

- **The domain registrar account.** Whoever controls the nameservers serves the app origin and
  captures passwords at the sign-in form. The shortest company-ending chain that Cloudflare
  authority does not already subsume.
- **The Cloudflare and GitHub accounts.** Between them they hold every secret in the inventory.
  Hardware-key MFA with no weaker fallback, and recovery codes held offline.
- **The Cloudflare Access hardware keys**, including the pre-enrolled backup — the only
  authentication path into the admin plane (`docs/ARCHITECTURE.md` §Admin plane).
- **The APNs authentication key** uploaded to Firebase, re-issuable at Apple; Apple caps a team at
  two, so revoke before minting at the cap.
- **Vendor console logins** for every service that issued a credential above.

## Adding a secret

1. Add the registry entry with its `credential` declaration, or the `ci-secrets.ts` entry for a
   workflow-only secret. The tests tell you what is missing.
2. Run `pnpm generate:env`; commit the regenerated blocks and this document's inventory.
3. Mint the value, write its offline copy, then set it in GitHub.
4. The family's runbook exists before the declaration does, with its obtaining steps, and with
   a replacement procedure when the class is `adminAction`. A new family is a new file.
